## Приоритет 2 — главный функциональный пробел

### 2. Reconciliation-экран (Tracker vs ПП) не достроен
Фундамент готов: импорт отчётов ПП (`/networks/{id}/reports`, таблица `core.pp_reports`, маппинг колонок).
Самого экрана сравнения — НЕТ (контроллера/вьюхи `reconcil*` не существует).
Это ровно про «фиксировать заработок честно»: видим свои конверсии, но не ловим расхождение с выплатами ПП.
**Фикс:** экран `/admin/networks/{id}/reconciliation` — запрос, объединяющий
`conversion_events` + `clicks` (наша сторона) с `pp_reports` (сторона ПП) по network+date+event_type,
LEFT/FULL JOIN → таблица «Дата / Событие / Наше / ПП / Дельта / Дельта%», подсветка расхождений > порога.
Обсудить: дефолтный порог (5-10%?), Telegram-алерт при расхождении, второй уровень маппинга event_type
(наши reg/ftd/redeposit ↔ их «Registration»/«Deposit»). Детали — в плане [[project-tracker-slimtds]].

## Приоритет 3 — горячий путь редиректа

### 3. Синхронные побочки блокируют ответ посетителю
В `ClickHandler::handle()` до `return` выполняется:
- **Telegram AI-source алерт** — `TelegramNotifier::send()` — синхронный cURL, `CURLOPT_TIMEOUT=5s`
  (+3s connect). Если TG API тупит — реальный посетитель ждёт до 5с до редиректа. Срабатывает по условию
  (визитор с AI-источника за 24ч), но на живом трафике условие будет частым.
- **Запись клика синхронна** — durable queue для входящих кликов нет (для пикселей/исходящих постбэков —
  есть, непоследовательно). Если PG залочен/лёг — редиректы тормозят/падают вместе с ним.
  Это пункт из собственного Keitaro-ресёрча («redirect не должен зависеть от тяжёлой БД»).

**Фикс:** вынести оба из request-пути — fire-after-response (в FrankenPHP worker сложнее, чем
`fastcgi_finish_request`, надо продумать) ИЛИ durable queue (по образцу существующих
`pixel_events_inbox` / `postback_deliveries` outbox). TG-алерт — точно в outbox/очередь.

### 4. Лишние SELECT на hot-path
`resolveFpJs` — SELECT на каждый клик; AI-алерт — ещё один SELECT при условии. Индексированные, суб-мс,
но на пике — латентность. Возможно объединить/кэшировать или увести в тот же async-путь, что и п.3.

### 6. Doc/reality drift
`CLAUDE.md` пишет «Click is logged async to stats.clicks» — код синхронный (`logClick` → `db->execute`

что «тест» здесь = ручной weighted-split, не эксперимент-фреймворк. Обсудить, надо ли автовывод.

## Приоритет 2.5 — сверка с постбек-эссе (2026-08-17)

> Пользователь принёс развёрнутое эссе про «как проектировать postback-движок самописного трекера».
> Сверил с фактическим `PostbackController` + схемой. Вывод: ~70% пунктов эссе у нас УЖЕ реализованы,
> местами лучше (append-only `conversion_events` ledger, идемпотентный `ON CONFLICT DO UPDATE`,
> `pg_advisory_xact_lock` от гонки, полная атрибуция к клику, UUIDv7 click_id, `postback_requests`
> raw-log на каждый удар). Эссе даёт РЕАЛЬНО новыми только 3 пункта ниже + один guard.

### 8. Нормализация ЗНАЧЕНИЙ событий (не только статусов)
Статусы приводятся к канону через `status_map`, а `event_type` — свободный текст без enum и без маппинга
значений. `AffiliateNetworkAdapter` переименовывает *параметр* (`goal`→`event_type`), но не переводит
*значение* (`firstDeposit`/`FTD`/`goal=2` → единый `ftd`). На 3+ ПП статистика разъедется на дубли-синонимы.
**Фикс:** второй уровень маппинга по образцу `status_map` — `event_map` (jsonb) на `affiliate_networks`,
канонический enum (registration/ftd/deposit/cpa/revshare/withdrawal/chargeback).

### 9. Валидация источника постбека — ТОЛЬКО token, ничего больше
Ни IP-allowlist, ни подписи. Token живёт в query-строке → утечёт в логи/реферер/скриншот в чате ПП →
любой накидает фейковых FTD/revshare руками через curl. Это прямые деньги, не «неплохо бы».
**Фикс:** добавить на `affiliate_networks` поле `allowed_ips` (многие сети публикуют статические
постбек-IP) и/или secret-подпись (HMAC от query). Проверять до записи конверсии. Лучше оба.

### 10. Revshare + retention — молчаливая потеря дохода ⚠️ самый неочевидный
`retention_clicks_days = 365` по умолчанию, `partitions:rotate` физически ДРОПАЕТ партиции кликов старше
retention (`dropOlderThanRetention()`). Revshare по игроку капает годами → постбек по click_id старше года →
партиция удалена → `click not found` 404 → доход потерян МОЛЧА, без единого следа кроме строки в
`postback_requests`. Для CPA 365д норм, для revshare click_id как ключ ломается.
**Фикс:** явно решить — либо revshare-клики не чистятся никогда (отдельная политика retention по типу
события), либо для revshare долгоживущий ключ = `player_id`/`external_id` вместо click_id. Обсудить с
пользователем, не выбирать самому.

### 11. Дедуп-guard от кросс-клик задвоения (дополнение, НЕ переделка)
Текущая идентичность `UNIQUE(click_id, event_type, COALESCE(external_id,''))` — правильная для SEO
(привязка к клику = атрибуция). Слабое место: один `transaction_id` по РАЗНЫМ click_id (ошибка ПП,
игрок с двух устройств) не поймается как дубль.
**Фикс:** оставить click_id-идентичность (атрибуция цела), ДОБАВИТЬ вторичный guard
`UNIQUE(network_id, external_id)` как страховку от задвоения по txid. Дополнение, не замена.

### 12. Telegram-send синхронно и в постбек-пути тоже
`PostbackController` (строка ~462) вызывает `TelegramNotifier::send()` (5s timeout) в потоке до отдачи 200 —
тот же баг, что в `ClickHandler` (п.3). ПП ждёт 200, мы залипаем на TG → провоцируем retry-шторм от сети.
**Фикс:** тот же, что п.3 — увести TG в outbox/очередь. Здесь даже важнее, чем в клик-пути, т.к. ретрай
постбека = задвоение попыток.

## ⚠️ Общее предупреждение: могут быть дыры, не видимые на первый взгляд
Всё выше — то, что нашлось чтением кода и сверкой с эссе. Это НЕ значит, что список полный. Трекер
работает с деньгами и внешним недоверенным вводом (постбеки от ПП, клики от кого угодно), и через него
не прошло ни одного реального клика с прода — только dev-докер и мои крэш-тесты. Классы дыр, которые
статический просмотр в принципе плохо ловит и которые вылезут только под живым трафиком / временем:
- гонки и порядок событий под реальной параллельностью (не 15 curl'ов, а тысячи в секунду);
- накопительные эффекты (рост партиций/диска, деградация индексов, раздувание ledger);
- поведение на границах (смена месяца/партиции, переход через retention, timezone/DST в отчётах ПП);
- доверие к данным ПП (кривые валюты, дубли txid между разными сетями, отрицательный/NULL payout в неожиданных местах);
- фрод и подделка (спуф IP, угон токена, replay постбеков) — частично п.9, но не только;
- интеграционные сюрпризы конкретных ПП, которые не описаны в их доке и всплывут на первом же реальном подключении.
**Вывод:** перед серьёзными объёмами — не полагаться только на этот список. Нужен период живого трафика на
малом объёме + мониторинг (Golden Click, unknown_click_id alert — п.5) как способ ЛОВИТЬ невидимое сейчас,
а не только чинить уже найденное.

## Готовность к VPS (отдельный вопрос)
Ни один пункт выше не блокирует деплой на VPS. Инфраструктура для прода уже есть:
`docker-compose.prod.cf.yml` / `.prod.direct.yml`, 3 режима (`cf_flex`/`cf_full`/`direct`),
`RealIp` с trusted-proxy, Caddy auto-TLS. Перед проливом на VPS — только: (1) git, (2) реальный `.env`
под прод-режим, (3) `partitions:rotate` в кроне (уже в crontab), (4) проверить sizing под ожидаемый RPS.
Синхронный клик (п.3) стоит закрыть до серьёзных объёмов, но для старта не блокер.
